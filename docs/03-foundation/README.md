## 2. 三项怎样连起来：以素材上传为例

| 动作 | 数据要留什么 | 规则决定什么 | 指标如何观察 |
| --- | --- | --- | --- |
| 接收素材 | 原件引用、文件属性、来源、缺失项与血缘 | 接收不等于母版确认；损坏、错配分别处理 | 入库必要条件完整性；失败/待补数量单列 |
| 确认母版 | 权威视频身份、修订、可用声音与附件关系 | 不覆盖原件，换母版新身份；派生音轨另存 | 缺项及返工事件可回查；不将时长接近算正确匹配 |
| 确认任务单 | 目的、范围、源/目标语言、市场/受众、输出与责任 | 人确认目的；代码检查条件；源语专用明确不适用 | 就绪完整率按任务类型与阶段统计 |
| 发起ASR | Task修订→Run输入→候选→审核记录 | 输入固定、权限/预算检查；人工稿不被覆盖 | WER/CER、边界误差、人工时间、失败；缺金标不报准确率 |
| 批量接受 | 展示候选、目标修订、逐条决定与撤销 | 先预览、提交重验；阻断项跳过 | 批次拆到单条候选，展示去重；编辑后接受不算直接接受 |
| 回滚/检查输出 | 恢复来源、新修订、失效检查、交付文件引用 | 回滚不抹历史；旧批准不自动继承；导出不等于发布 | 回滚和返工保留，首轮通过不能被重试刷新 |

Task为业务任务单，Run为一次模块执行；课件§4.1把单次执行称task_id，本项目显式改用run_id，避免与母版关联的任务单混淆。Run的重试仍属同一次执行的attempt，不制造新的有效建议来提高接受量。

## 3. 六个思考维度的交叉检查

| 课件§0.5维度 | 数据 / 依据 | 规则 / 人工分工 | 指标 / 验收方向 |
| --- | --- | --- | --- |
| 正确性 | 源片段、原文/候选/人工版本、金标 | 模型提建议；代码保护术语/数字等；人核实 | WER/CER、风险召回、术语、语义保护，不能只看接受率 |
| 可读性 | 显示时间、语言profile、文本与断句 | 代码算CPS/行长；模型提供语义候选；人确认 | CPS、边界偏差、断句；字符统计需按profile定义 |
| 文化与法律 | 市场/分级/证据/规则版本 | 红线须有效适用依据；创作意图与争议交人 | 按市场/等级分桶召回、提示有效性及证据完整性 |
| 可交付性 | 检查快照、平台规范、导出产物与哈希 | 确定性校验、人工签发、外部回执分开 | schema、首轮通过、导出一致；无回执不冒称平台通过 |
| 可治理性 | 身份、版本、manifest、操作/失败/决定日志 | 服务端权限、版本校验、幂等、停止与升级 | 追溯覆盖、越权成功和绕闸；无请求时不能报零风险 |
| 效率 | 人工活动、等待、返工、运行成本与可比批次 | 安全不能被速度抵消；只重做受影响节点 | 净人工分钟/成片分钟、TAT、成本；完整人工时间防止复核重复扣除 |

这些是质量/治理/效率视角；课件§3.3内容、音频、语言、市场、平台、风险、治理是配置和分层变量；六处理模块是执行职责。三种分类不能因数量相近就等同。§0.7原文实际列五类冲突，详见规则注册表；并非冲突只有五种。
